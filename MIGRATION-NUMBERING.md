## Do not fix this by renaming the file

Renaming leaves the snapshot stale: it was generated by diffing against `0255`, so
it does not contain `0256`'s tables. `drizzle-kit check` still passes, but the next
`drizzle-kit generate` re-emits the other branch's DDL and that explodes on a
database which already has it. Regenerate instead:

```bash
cd <your worktree>
git merge origin/main                    # journal now tops out at main's newest
git checkout --theirs src/db/migrations/meta/_journal.json \
                      src/db/migrations/meta/0256_snapshot.json
git rm src/db/migrations/0256_<your-name>.sql
git commit
npx drizzle-kit generate --name <your_name>
diff <the old .sql> src/db/migrations/0258_<your_name>.sql   # must be identical
npx drizzle-kit generate                 # must print "No schema changes"
```

## Check the `when`, or the migration silently never runs

`drizzle` applies a migration only if the database's newest `created_at` is **below**
that migration's journal `when`. After regenerating, compare your entry's `when`
against **each** database's newest `created_at`, not against main's journal:

- **PROD** newest is `1788451061636` (`0256_observation_audience_context`).
- **DEV** already has more applied than prod — check it before assuming.

If your DDL is already applied on dev, keep the *original* `when` so dev skips it
while prod still applies it. That is what `fund-portfolio-to-model` did: its `when`
stayed `1788479423596`, which is above prod's newest and equal to its own dev ledger
row, so it applies on prod and is correctly skipped on dev. Bumping it to the
regenerated timestamp instead would make dev try to re-run the DDL and roll back the
whole transaction.

⚠️ A push to `main` **is** the deploy and never runs `migrate`. Apply your migration
to prod *before* pushing.
